## 1. What is measured

Ground truth exists only for the 32 public samples (`dataset/sample_output.csv`), so accuracy is measured there. The 518 evaluation requests have hidden answers; for them we report consistency checks, model comparisons and the output distribution. Custom cases (section 5) test behaviour the samples do not cover.

| Metric | Definition |
|---|---|
| Case-level status accuracy | `deletion_status` equals the gold status |
| Step precision / recall / F1 | a step counts only if phase, operation, state, system_id, resource_id and evidence_id all match |
| Field-level accuracy | per field, over gold steps aligned by (system_id, resource_id, operation) |
| Sequence accuracy | the entire `steps_json` array is identical, order and step numbers included |

## 6. Failures found and improvements made

Each row is one iteration on the samples (status / step precision / step recall / sequence accuracy).

| # | Change | Status | P | R | Seq | What the failure taught us |
|---|---|---|---|---|---|---|
| 1 | First end-to-end pipeline (evidence readers, identity, intent, policy planner) | 96.9% | 95.1% | 89.6% | 56.3% | Deleted accounts (404, no identifiers) and anonymized analytics could not be linked to the person; one remaining record was overridden by an empty inventory table. |
| 2 | Workflow reconstruction: account event mirrors the reported claim; joint assignment across all requests; seconds-phase fingerprint links later workflow steps; inventories no longer prove absence | 100% | 98.9% | 95.9% | 75.0% | Claim->result mapping held for 252/252 independently linked accounts. |
| 3 | Decoy guard (negative lookups before the request are ignored), fingerprint tie-break by phase error, legacy window, bundle snapshots as absence evidence | 100% | 97.3% | 94.3% | 71.9% | Regression: absence-by-omission in a later bundle overrode explicit read-backs. |
| 4 | Absence-by-omission used only when no explicit observation exists | 100% | 100% | 97.9% | 90.6% | Explicit evidence (404 read-back, found record) must outrank inference. |
| 5 | Local OCR for screenshots, LLM intent cross-check, vision-model screenshot reading | 100% | 100% | 97.9% | 90.6% | Samples unchanged; 5 evaluation story cases corrected where OCR could not judge state. |
| 6 | Verification only when evidence proves the state; absence inference only for delete-category records | 100% | 100% | 97.9% | 90.6% | Unknown state had been treated as compliant; retained records were wrongly inferred absent from partial replica tables. |

Traps found in the data and how the agent handles them:

- **Claims vs truth:** workflow statuses and activity results (`SUCCESS`, `PARTIAL`, `DELETION_PENDING`) are never proof; only point-in-time evidence decides.
- **Decoy identities:** near-identical emails (`g.silva76.jr@` vs `g.silva76@`) and months-old negative look-ups that point at someone else's account. Only exact identifiers link, and negative look-ups only count after the request was made.
- **Historical identifiers:** in 80 evaluation cases some data is reachable only through an old email, phone or hash; 100 requests are written from an old address.
- **Replication drift and re-creation:** copies surviving in replicas, and connectors that repopulate deleted records; flows are disabled before dependent records are changed.
- **Time cut-off:** evidence captured after `audit_at` is never used, and the cut-off is inclusive (confirmed by a sample that cites evidence captured exactly at `audit_at`).

## 7. Known limitations and next steps

- The workflow fingerprint relies on the timing structure of this dataset; a production system should require correlation ids on every workflow event instead of timing forensics.
- When several accounts of the same claimed result are deleted in the same window and no other step disambiguates them, the joint assignment can still pick the wrong one.
- The legal-retention register PDF lists held orders by order number and user, but no resource ids, so it cannot produce steps.
- Retention expiry is not enforced: every retention date in the data (2027-2034) is after every audit date, so it does not change any answer, but production code should schedule deletion when retention ends.
- Rule-based intent covers six languages; other languages rely on the LLM layer (custom_06).

## 8. Real-world scenarios we reviewed

Scenarios raised while stress-testing the design, with what the data shows:

| Scenario | What the data shows / how the agent handles it |
|---|---|
| Login identifiers (email, phone, username, social login, device) | Only user_id, email, phone and email hash exist; all historical values are matched; no format variants exist (73/76 evidence phones match a known phone exactly, the rest belong to no known user). Names are not used for linking (ambiguous). |
| Still-logged-in devices after deletion | Sessions are not modelled; the security log shows 'Session revoked' before 'Account closure recorded'. Production: revoke sessions and tokens before deleting. |
| Grace periods across time zones | All 10,977 timestamps are UTC; comparisons are instant-based and the cut-off is inclusive. |
| Warranty, tax, payment disputes | Legal holds (8 records, `payment_dispute_and_tax_record`) and security logs are retained and verified present, never deleted; tombstones keep only the stable user reference. |
| Profile changes just before deletion | 80 cases have data reachable only via old identifiers; all are covered. |
| Pending returns or orders | Order-context support chats are redacted, not deleted (rule_05); `DELETION_PENDING` rows still holding an email are treated as present. |
| Promotional copies (Black Friday lists, audiences) | Marketing profiles deleted, identifiable analytics anonymized, warehouse connectors disabled first. |
| Accidental loss in a disaster | Not a valid deletion (a breach); the agent never treats missing evidence as proof: COMPLETE verifications cite evidence. |
