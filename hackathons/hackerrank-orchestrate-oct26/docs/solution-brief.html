The problem, in plain words

Northstar Shop (imaginary) told a customer their account was deleted: every dashboard said "Complete". Weeks later the same customer tried to sign up again and was refused: "This email is already registered." The deletion had removed the main record, but copies of the person's data lived on in many other places, and a sync job had even re-created what was deleted. The company lost $2.4 million.

Analogy: you ask a shop to shred your paper file. They shred the main file and say "done", but there are photocopies in other branches, your name in their phone book, your complaint letters in the help-desk folder, your address on the marketing list, and boxes in the archive. An assistant even keeps re-copying from an old copy.

What the agent must answer for each of the 518 requests

  • NOT_APPLICABLE: the person did not ask for deletion (fix my name, send me my data, marketing only...).
  • COMPLETE: everything is correctly treated; list the verification checks with the evidence that proves them.
  • INCOMPLETE: report what remains, the ordered remediation plan, and the checks that must pass afterwards.

Real-world context: this is the GDPR / CCPA "right to erasure". Regulators have fined companies when "deleted" data survived in copies (e.g. reported cases involving Amazon Alexa, Morgan Stanley, Deutsche Wohnen).

How we solve it

1 IntentMultilingual rules with negation handling; Claude gives an independent verdict
2 Identityuser_id + every old email, phone and SHA-256 hash
3 Discovery94 files → one list of observations; workflow reconstruction
4 StateLatest evidence at or before audit_at; claims never count
5 Policydeletion_rules.csv per category
6 StepsOrdered findings → remediation → verification; validated

Key ideas

One shape for all evidence. SQL (executed in SQLite, primary vs replica tables), JSON, nine log dialects (start/complete events joined by trace id), text, PDF and OCR/vision output all become observations: resource, time, state, identifiers.
Evidence beats claims. "SUCCESS", "PARTIAL" and "DELETION_PENDING" are claims. A 404 read-back, a found record or a replica row decides. Explicit observations outrank absence-by-omission.
Workflow reconstruction. Deleted accounts (404) and anonymized profiles carry no identifiers. The account event's result mirrors the reported claim (252/252 validated), and each workflow's later steps share a seconds-phase fingerprint. Accounts are assigned jointly so one event serves one workflow.
Policy-correct ordering. Disable flows and block restores first, then delete / redact / anonymize, then verify. Retained records are verified present, never deleted. COMPLETE verifications are written only when evidence proves them.

  • Stress-tested the design with real-world scenarios (section 6), several of which became checks and report content
  • Required plain-language understanding of every part before submission
Claude Code (pair programmer)
  • Reverse-engineered the dataset against the 32 samples, hypothesis by hypothesis
  • Implemented the readers, linking, policy planner, evaluation workflow and reports
  • Ran every experiment and reported failures honestly (e.g. iteration 3 regression)
  • Kept the transcript (log.txt) and kept secrets out of chat, logs and the zip

Honest limitations

  • The workflow fingerprint is specific to how this dataset was generated; production systems should use correlation ids.
  • Some accounts deleted in the same window with the same result can still be matched to the wrong workflow.
  • The legal register PDF lists held orders but no resource ids; retention expiry is not enforced (no dates expire in the data).

Interview cheat sheet

60-second pitch. "My agent audits deletion requests the way an investigator would. It first checks whether the person really asked for deletion, then finds every identifier they ever used, reads all 94 evidence files into one timeline, and decides each record's state at the audit time from evidence, never from status labels. Deleted accounts and anonymized records have no identifiers left, so I reconstruct the deletion workflow from the activity stream. Then the policy table decides delete, redact, anonymize or keep, and the steps are ordered so nothing can re-create the data. AI is used where interpretation is needed: Claude cross-checks intent and reads screenshots. Decisions stay deterministic. It scores 100% status accuracy on the samples, costs $0.0018 per request, and every number is reproducible with one command."
Why not let the LLM decide everything?
Reproducibility, cost and explainability. Every decision must cite evidence and give the same answer on every run. I used the LLM where text or images need interpretation, measured it against the rules (550/550 agreement) and cached it.
How did you know the answers were right without labels for the 518?
Accuracy on the 32 labelled samples, contract validation of all 518 rows, independent model comparisons (rules vs LLM, OCR vs vision), an ablation study, and metamorphic custom cases.
What was the hardest part?
Records with no identifiers left. I found that each workflow's events share a seconds-phase pattern and that the account event mirrors the reported claim (validated 252/252), and used them to assign accounts jointly. I'm also clear this is dataset-specific forensics; production needs correlation ids.
How did you use AI while building?
Claude Code was my pair programmer: it analysed the data, proposed hypotheses, wrote the code and ran experiments. I set direction, made the decisions (scope, adding the AI layer, priorities), stress-tested the design with real-world scenarios and reviewed results. The whole process is in log.txt.
What would you change for production?
Correlation ids instead of timing forensics; session and token revocation; retention-expiry scheduling; time-zone normalisation at ingestion; propagation of deletions to third-party processors; automatic re-audits.
Complexity and cost?
O((n·k + m) log m): hash indexes plus time-sorted binary search for activity windows. About 4 s for the full run. 25 model calls, 232 tokens and $0.0018 per request, cached for free reruns.
